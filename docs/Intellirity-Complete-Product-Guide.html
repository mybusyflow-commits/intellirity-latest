01 · Executive summary

What Intellirity is

Intellirity is an AI security platform. It checks the text, code and actions that surround a language model or autonomous agent, decides whether they are safe, and records proof of the decision.

AI applications are different from ordinary web applications. They accept free-form language, retrieve content from the internet, call tools, spend money and make decisions with incomplete instructions. A traditional firewall can see a request; it cannot see that a retrieved web page is trying to instruct the model, that an agent has been quietly redirected to a new goal, or that a generated code block contains a live database password.

Intellirity adds a security layer around those behaviours. It runs sixteen deterministic detection engines — no “ask another model whether this looks bad” dependency for the core verdict — and exposes them through a marketing site, a free scanner and an authenticated console. The commercial product is split into nine buyable modules so a customer can pay for the coverage they actually run.

02 · The problem

The problem we solve

AI systems fail in ways that ordinary application security does not model. Intellirity was built around those failure modes, not around a generic “AI firewall” label.

2.1 The core risk: text becomes authority

In a normal application, data and instructions are structurally separate. In a language model, both arrive as text. A retrieved web page, PDF, email, code comment or tool result can contain instructions the model follows as if they came from the application owner. This is indirect prompt injection. A user can also try to override the system prompt directly — that is direct prompt injection or a jailbreak.

The consequence is not just an embarrassing answer. If the model has tools, the consequence is a database query, an email, a payment, a file write or a cloud API call.

2.3 Why a WAF is not enough

A WAF understands HTTP methods, paths, headers and known payload signatures. It does not understand that a paragraph inside a support ticket is attempting to change an agent’s objective, or that a model output is about to be rendered as HTML. Intellirity sits at the semantic layer: before the model consumes text, before a generated artefact is trusted, and before an agent action is released.

2.4 The design principles behind the product

  • Deterministic first. The detection engines are regex, statistical and state-machine analysers. They do not depend on an external LLM to produce a verdict.
  • Fail closed. If an engine errors in the screening path, the request is denied rather than forwarded unchecked.
  • Evidence by default. A verdict is useful only if it can be reconstructed. The ledger is append-only and hash-linked.
  • Per-module commerce. A customer should not have to buy the entire platform to solve one problem.
  • Tenant isolation. A user or Clerk organisation owns its own workspace, billing, models, policies and escrow.

06 · Request lifecycle

What happens when a scan runs

One request passes through identity, tenancy, plan enforcement, one or more engines, scoring, logging and evidence. This is the path to explain in any technical review.

  1. Identity. The request carries either a Clerk bearer token (human), an X-API-Key (machine) or, in local development only, an open-mode identity. An invalid key is always rejected.
  2. Tenant resolution. An active Clerk organisation becomes org:<id>; without one the user owns user:<id>; a machine key owns its own service tenant.
  3. Entitlement hydration. The API loads that tenant’s paid modules from Postgres when the instance cache is empty or older than 120 seconds. This is what makes a purchase work across serverless instances.
  4. Plan enforcement. Each requested engine maps to a product. If the tenant does not own the product, the engine is denied. Free engines remain available.
  5. Input bounds. Text fields are capped, code scans have a size limit, URL scans resolve DNS and refuse private, loopback, link-local or reserved addresses.
  6. Engine execution. The engine runs deterministic rules, state machines or statistical checks. A multi-module sweep runs independent engines concurrently.
  7. Scoring. Findings are weighted by severity; the module returns a risk score, findings, severity and verdict. Bands differ by engine but generally map to allow / flag / block.
  8. Response shaping. The UI receives structured JSON. API responses are private, no-store with an authorization-aware Vary header.
  9. Evidence. A high or medium risk event can create a threat record. Ledger writes are chained and persisted. Escrow transitions are validated and persisted.
  10. Activity. A completed scan writes a small activity row (owner, type, risk, time) used by the real charts. The raw prompt is not written there.

What the client sees

The scanner returns a terminal-style report with a verdict, risk, per-engine findings and locked-module notices. The console overview shows the workspace’s active modules, real scan volume, open threats and KPI strip. Free scanner users see only the relevant findings and fixes.

Failure behaviour

If an engine raises, the module API returns an error instead of a fabricated verdict. In the screening-proxy path, a failure is a deny, not a pass. The UI surfaces a clear timeout or error rather than leaving a progress bar running forever.

7.1 Jailbreak & Injection Protection

The free entry point and the most used engine. It combines seventeen pattern families and 113 patterns covering direct instruction override, “ignore previous instructions”, roleplay/persona jailbreaks, safety-disabling language, encoded payloads (base64 and similar), prompt-extraction attempts and exfiltration framing. It supports an input or output direction, returns a sanitized-text field, a recommendation and the list of modules triggered.

7.2 Advanced Threat Intelligence

A broader adversarial layer for teams that need more than the free engine. It maintains a threat catalogue and pattern families across prompt injection, jailbreak, obfuscation, data exfiltration, agent abuse, privilege escalation, MCP abuse, model supply chain, denial of service and behavioural drift. It correlates multiple signals rather than returning one regex hit.

7.3 Vibe Code Security

Two products share the name: a free public scanner for a URL or pasted code, and the paid repository review inside the console. The module looks for SQL injection, dynamic SQL, XSS sinks, command execution, SSRF, path traversal, insecure deserialization, weak crypto, hardcoded secrets, unsafe random generation, ReDoS and more. The repository path adds per-file line numbers, CWE, confidence, fix effort, a derived threat model, coverage, an ordered remediation plan and a SARIF 2.1.0 report. It does not execute the code.

7.4 AI Model Supply Chain Security

Reviews the model source and format before deployment. Unverified/community/unofficial sources are flagged; an expected SHA-256 can be compared; pickle formats are treated as code-execution risk; caller-supplied known vulnerabilities are included. It returns a block/flag/allow verdict and a deployment recommendation.

7.5 Data Loss Prevention

Detects email, US SSN, phone, credit-card-shaped numbers, IP addresses and date-of-birth context; cloud keys, GitHub tokens, Stripe keys, Google API keys, Slack tokens, JWTs, private-key blocks and password assignments; SQL/XSS/code-execution output; and customer-supplied regex patterns. The action escalates from log to redact to block.

7.6 Data Flow Tracker

Maps each pipeline stage and destination. It flags destinations on a blocked list or outside a trusted list, sensitive fields accessed by a sensitive/restricted classification, destructive tool calls, external callback URLs and excessive reasoning-chain length.

7.7 Content Moderation

Seven categories with independent pattern families and a weighted score. The engine deliberately allows mild profanity and keeps the severe terms narrow to reduce false positives. Minor-safety sexual framing is treated as critical.

7.8 AI Action Policy Enforcer

Evaluates an agent action, action type, tool calls, session context and policy object. It returns allowed, violations, abuse categories, risk score, critical count and a recommendation. This is the policy layer behind the Policies console page.

7.9 Behavioural Analysis Engine

Compares the current action against session history. It reports actions analysed, anomalies, behavioural drift, risk level and a recommendation. It is designed for traces, not one-off prompts.

7.10 MCP Security & Tool Governance

Checks MCP servers and tool calls for poisoning, confused-deputy patterns and tools outside the allowed set. It returns servers checked, tool calls checked, findings, risk and status.

7.11 Workflow Anomaly Detector

Ingests a workflow’s actions with cost and duration. It detects repeated action sequences, excessive iterations, spend above a configured ceiling, timeouts and cascading side effects. The console turns a comma-separated action list into that payload.

7.12 Denial-of-Wallet Protector

Detects API loops, token and cost ceilings, unusual call counts and resource exhaustion. It returns alerts, total tokens, total cost, call count, risk and an action, and is wired to the Wallet page.

7.13 Autonomous Escrow

A real state machine: held → released or held → rejected, exactly once. It rejects unknown IDs, invalid amounts and replays. Holds are persisted in Postgres and restored across instances.

7.14 Black Box Ledger

Append-only records sealed with a hash that commits to the previous record; a Merkle root summarises the set. Verification walks the chain and reports tampering. In production the database is the authority: appends are serialized against the database tail so multiple processes cannot fork the chain.

7.15 Verifiable Proof of Intent

Issues an HMAC-SHA256 certificate containing the human ID, instruction hash, action scope, timestamp, expiry and nonce. Verification rejects a forged signature, an expired certificate and an action outside the signed scope. This is proof that a human authorised a class of action, not proof that the model behaved.

7.16 Threat Intelligence Feed

Returns a catalogue of known AI attack patterns with type, severity and indicators. Currently this is a curated static catalogue of eight patterns, not a live external intelligence subscription. It is useful as a reference and UI feed; it should not be sold as a continuously updated commercial threat feed without adding that data pipeline.

10 · Free scanner

Vibe-Code Security, free and paid

This is the lowest-friction product surface and one of the most important differentiators. A visitor can get a real security result without signing in, paying or reading documentation.

10.1 The free public scanner

URL: https://www.intellirity.com/free-scan. Two modes:

  • Website URL: resolves the host through the SSRF guard; refuses private, loopback, link-local and reserved addresses; does not follow redirects blindly; reads up to 300 KB of HTML; checks transport, HSTS, CSP, X-Frame-Options, X-Content-Type-Options, X-Powered-By, CORS, cookie flags, mixed content, external scripts without SRI, inline-script code patterns and page-source secrets.
  • Paste code: runs the same Vibe-Code detector registry on up to 50,000 characters. Findings include severity, CWE, line and a concrete fix.

Limits are deliberate: a scan is not an exploit, does not authenticate, does not crawl the whole site and does not brute-force endpoints. The UI states this. The endpoint is rate-limited and records only activity metadata (type, risk, time), not the scanned URL or code.

10.2 The paid repository review

Inside /console/code, a workspace that owns Vibe-Code can choose a folder or files. The browser reads them locally and sends a bounded JSON snapshot:

LimitValue
Maximum files300
Maximum single file200,000 characters
Maximum total snapshot1,500,000 characters
Skipped filesBinaries, assets, duplicates, oversized files and exhausted budget are listed in coverage

The review returns: per-file findings with line, rule ID, severity, CWE, confidence and fix effort; an ordered remediation plan; a threat model derived from routes, auth, uploads, outbound calls, shell execution, data stores and literal secrets; coverage with skipped-file reasons; and a SARIF 2.1.0 download for CI.

Repeated findings are grouped per rule and file, with a true occurrence count, and the report is capped at 300 groups. This prevents a repeated line from creating a 15 MB response.

10.3 Dependency and manifest review

Package manifests are parsed for risky and unpinned dependencies. The current risky-package list includes vm2, node-serialize, event-stream, serialize-javascript, PyCrypto, request, node-sass, moment and left-pad. This is a review prompt, not a live CVE database; versions are reported as written and no lockfile resolution is performed.

10.4 What it does not do

  • It does not launch a Docker sandbox or actively exploit a target.
  • It does not authenticate to the customer’s application or crawl behind a login.
  • It does not guarantee absence of vulnerabilities after a clean scan.
  • It does not replace a manual penetration test or a compliance audit.

10.5 The autonomous half

The reference project behind the Vibe-Code concept includes an autonomous agent that plans tests, uses tools, runs a sandbox and writes exploit evidence. That requires a Docker-capable worker, outbound internet and an LLM API key. It cannot run inside a request-scoped Vercel function. Until that worker is deployed, do not sell “autonomous exploit validation”. The static scanner, repository review, threat model, coverage and SARIF are live.

12 · Payments

Payments, settlement and refunds

The checkout is a PayU hosted redirect. The code verifies payment; it does not move money. Settlement is a merchant-bank function inside PayU.

12.1 Checkout flow

  1. The signed-in buyer selects modules and enters name, email and a valid phone number.
  2. The server prices the order from the catalogue and stores it in Postgres with status pending-payment.
  3. The server builds a PayU form with a SHA-512 request hash: key, txnid, amount, productinfo, firstname, email, udf1–udf5 and salt.
  4. The browser POSTs the form to PayU’s hosted checkout.
  5. PayU posts the result to /backend/billing/payu/callback. The server verifies the reverse hash.
  6. On success, the order becomes active and entitlements are written to Postgres. Replays are idempotent; an existing order is not granted twice.
  7. If the callback is lost, the pricing page calls /payu/sync. The server asks PayU directly, checks the captured amount equals the order total, and grants the modules.

The “enhance your customers’ checkout experience” prompt in the PayU dashboard is checkout customization, not settlement. It can be skipped.

12.3 Settlement: why money may not reach the bank

A PayU dashboard transaction can be successful while the money is still held or routed to a different bank account. The application cannot change this. The merchant account controls it.

CheckWhat to verify
Merchant accountThe dashboard MID and merchant key must match the key used by the backend. A different PayU account has a different bank account.
Live vs testTest transactions show amounts but never settle. Confirm the transaction is in the live dashboard.
Bank detailsA verified settlement bank account must exist on the MID: correct account holder, account number and IFSC, with penny-drop/verification complete.
KYC / activationAn account can accept transactions while settlement is on hold pending KYC, website verification or activation.
Settlement cycleUsually T+1/T+2 business days. Weekends and bank holidays shift the date.
Minimum payoutSome merchant accounts have a minimum settlement amount. A single small payment can remain below the threshold.
UTRIf the transaction shows a UTR, PayU released the money; give the UTR to the bank. No UTR beyond the cycle means a PayU support case.
Reserve / holdRolling reserve, chargeback hold or risk review can delay settlement.
Sales-safe answer

“PayU confirms the payment to us and we unlock the modules immediately. Settlement to your bank is handled by your PayU merchant account. If the dashboard shows a successful transaction but the bank has not received it, send the txnid, mihpayid and UTR (if any) to PayU support with your MID.”

12.4 Refund mechanics

Refunds are issued through PayU against the original transaction. Intellirity does not store card numbers or UPI credentials. A refund request needs the order ID, workspace email and reason; approval goes back to the original payment method.

13 · Data and identity

Data model, identity and tenancy

The tenant is the unit of isolation. A user or organisation owns its records; a machine key owns its own service workspace.

TableWhat it holdsDurability

Identity paths

  • Human: Clerk session JWT verified with RS256/JWKS (or HS256 fallback). Expired, forged or unsigned tokens are rejected.
  • Machine: X-API-Key, matched by SHA-256 hash; no raw key stored.
  • Open mode: only when no auth is configured and the environment is not production. Production without auth refuses to serve protected routes.

Tenant rules

An active Clerk organisation owns the workspace. Without an organisation, the user owns a private tenant. A machine key owns its own service tenant and is never written to the user table. Cross-tenant reads are 404, not “forbidden” with an existence leak.

Persistence caveat

Orders, entitlements, scan activity, threats, model endpoints, policy packs, ledger, escrow and contacts are durable in Postgres. The in-process store remains a fast cache/fallback, but a serverless cold start no longer erases the tenant’s threat history or workspace configuration. The audit ledger remains the permanent evidence record.

The security model

The product is sold as security software, so its own controls have to be explainable. This is what the deployed system actually enforces.

17 · Client conversations

How to answer the questions you will actually get

Short, accurate answers. Do not improvise beyond them.

Q1

“What exactly do you sell?”

Per-module AI security for 30 days. Nine modules from ₹79 to ₹399; free tier and free Vibe-Code scanner for evaluation. No seats, no platform fee, no auto-renew.

Q2

“Is this a WAF?”

No. A WAF understands HTTP. Intellirity understands intent: semantic injection, jailbreaks, agent actions, data flow, code and evidence.

Q3

“Does it call an LLM to decide?”

The core detection engines are deterministic regex/statistical/state-machine analysers. An LLM is used only for the optional reasoning/proxy features.

Q4

“Do you store our prompts?”

No by default. We process to return a verdict and store metadata/evidence according to the workspace retention policy. Scan activity stores type, risk and time, not payload.

Q5

“Can it stop an agent?”

It can evaluate the action, enforce policy, hold funds in escrow and require a signed human intent proof. It is a control layer, not a guarantee that the agent is correct.

Q6

“How fast is it?”

Most deterministic scans complete in well under a second; a URL scan adds a bounded page fetch up to eight seconds; repository review is a few seconds depending on size.

Q7

“What if an engine crashes?”

The screening path fails closed: deny rather than forward. The UI reports an error; it does not fabricate a clean verdict.

Q8

“Are you SOC 2 / ISO certified?”

Not yet. We do not claim certifications we do not hold. We can show the security model, controls, tests and policies.

Q9

“Can we self-host?”

Yes, as a sidecar inside your VPC. That is a separate deployment and commercial conversation.

Q10

“How do we pay?”

PayU hosted checkout in INR. Each payment covers 30 days. No card is stored by us; settlement is to the PayU merchant account.

Q11

“What is free?”

The injection engine, threat feed, free Vibe-Code URL/code scan and the free console pages. Paid modules unlock the deeper engines and repository workflow.

Q12

“What is missing?”

Autonomous exploit validation, durable threat/model/policy state, external intelligence ingestion, SOC 2/ISO and in-app refunds. Section 16 lists them.

The strongest pitch is not “we stop every attack.” It is: “we put a deterministic control and a reconstructable record around the places where AI text becomes an action — and you only pay for the controls you run.”
